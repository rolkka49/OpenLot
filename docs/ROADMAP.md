### Milestone 2.3 — Inspector property system
- [x] Scrollable Inspector section so long property lists stay usable (header stays pinned; the transform + property rows live in a scrolling child)
- [x] Typed property widgets: checkbox (bool), dropdown (enum/choice), plus the existing numeric/text fields
- [x] Per-object property set, starting with: Anchored, CanCollide, Texture
- [x] 2D wallpaper: `wallpaper` command opens a file browser and draws the image behind the ImGui dockspace (Terminal + Builder chrome, **not** the 3D sky); `wallpaper clear` returns to the default background. Drawn as an input-less full-viewport window under the dockspace. **The choice is remembered on disk** (`user://openlot_settings.cfg`, `[wallpaper] source_path`) and restored by `WallpaperService.LoadPersistedSettings()` from `Terminal._Ready` (and idempotently from `Builder._Ready`), so it survives both scene changes and a restart; a stored path whose file has gone is forgotten with a warning. That config file is the seed of §5.4's client settings rather than a second format. (Builder also gets a View menu entry.) The part Texture property and the wallpaper share one image-loading path (`LotTextureCache`) via `ImageFilePicker`. The loader sniffs the file's magic bytes and dispatches to the matching Godot buffer loader instead of `Image.LoadFromFile`, because that one picks by file **extension**: a downloaded WebP/JPEG named `.png` made Godot's PNG driver reject the file and print three engine ERROR blocks to the console. Sniffing fixes those files (they now load) and makes a non-image a single readable message with no engine noise. `OPENLOT_TEST_IMAGE=<path>` opts in to a check against a real file on this machine.
- [x] Semantics settled in code comments next to the storage. `CanCollide = false` moves the collision body to a reserved no-collide layer rather than disabling/removing the shape, because a disabled shape vanishes from raycasts and would make the part unselectable and undraggable in the editor — the milestone requires the opposite. `Anchored` is a **physics** property (anchored = stays in place, unanchored = affected by gravity in a player session), **not** a write lock: scripts may still position an anchored part. In Build mode both states stay put; gravity itself waits on §3.6's dynamic-body layer.
- [x] Properties are exposed through the bound Lua API, so scripts can read and set them (respecting the §1.1 boundary: no direct Godot access). Verb-first verbs now (`SetAnchored`/`IsAnchored`, `SetCanCollide`/`GetCanCollide`, `SetTexture`/`GetTexture`); the gated generic accessor lands later.
- [x] Property widgets are data-driven (a property declares its type and options), so adding a new property doesn't require new Inspector UI code. `LotPropertyRegistry` is the one declaration table, `Register()` is the Tier-2 plugin entry point, and `LotPropertyService` is the single write path (future §2.4 undo and §4.1 save hook here).
**Acceptance criteria:** A creator can select an object, scroll the Inspector, toggle Anchored/CanCollide with checkboxes, pick a Texture from a dropdown, and see the change take effect in the scene and in Lua.
**Verification:** `WallpaperSelfTest` (55 checks, including the on-disk persistence contract and an opt-in `OPENLOT_TEST_IMAGE=<path>` check against a real file) + `LotPropertySelfTest` (39 checks, including one that drives the real bound Lua API), both headless under `#if DEBUG` from `BuilderScene._Ready`; the 2D wallpaper's on-screen composition is a rendering result and is checked by eye in the running client.
**Difficulty:** 🟡 scrollable Inspector · 🟡 typed widgets · 🟠 data-driven property declaration · 🟠 Anchored/CanCollide semantics · 🔴 Texture + wallpaper (shared image-loading path, seeds §7.2 / §16.6)

### Milestone 2.4 — Editor workflow
- [x] Undo/redo across gizmo drags, Inspector edits and hierarchy operations (command stack; `MarkDirty` is the only history today). Commands are pushed by the existing single write paths (`BuilderScene` spawn/delete/duplicate/reorder/reparent, `LotPropertyService`, `ScriptManager`), commit on release/`IsItemDeactivatedAfterEdit`, and coalesce per drag rather than per frame
- [x] Code-editor edits join the same stack (`CodeEditorWindow`): one entry per editing session, committed when focus leaves the field and on window close, holding `(path, before, after)` and applying through a single `CodeEditorWindow.ApplyCode` that writes via `ScriptManager.SaveScript`. Recorded **only while the edited script's node is selected** — otherwise the editor stays a plain file buffer (still auto-saved). While the field has focus Ctrl+Z remains ImGui's own in-widget undo and the lot stack ignores it (`Builder._UnhandledInput` gated on an `IsItemActive`-derived focus flag, the same one-frame-flag pattern as `WantsMouse`). Entries whose file is gone (script deleted/renamed) are dropped rather than recreating a deleted asset. Undo/redo of a script edit does not re-run the lot — scripts still load at lot load (§3.2)
- [x] Drag objects in the hierarchy panel to reorder, and drag one object into another to reparent (`Reparent` exists; the panel had clicks + marquee only; ImGui drag-drop sources/targets are already in the wrapper). Rejects drops into a node's own subtree, onto internal children (`InternalChildMeta`) or `LotScriptNode`s, and across the `LotRoot`/`LotUIRoot` boundary. While a drag is in flight the hovered row shows where it will land — the row is tinted and outlined when the node will become its child, an insertion line is drawn on the edge it will be inserted at (so "between" vs "into" is never ambiguous), and an invalid target shows nothing at all
*(Autosave and crash recovery live in §4.1 (Phase 1): a periodic autosave to `user://autosave.lot`, a crash marker and a boot-time recovery prompt — on the same `.lot` writer a manual save uses (§4.2).)*
**Implementation status:** landed. `builder/EditorUndo.cs` holds `IEditorCommand`, `EditorHistory` and the node-lifetime / transform / script-edit commands; `builder/panels/HierarchyDrop.cs` holds the pure drop rules; the wiring runs through `Builder` (Edit menu, Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y, save-point dirty tracking), `BuilderScene`, `InspectorPanel`, `GizmoController`, `PartDragController`, `UiGizmoController`, `ToolboxPanel`, `ContextMenuUI`, `ScriptManager`, `CodeEditorWindow` and the `LotPropertyService` write path. Verified headless by `EditorWorkflowSelfTest` (82 checks) alongside `GizmoSelfTest` 176, `NetSelfTest` 169 and `NetIntegrationTest` 59 — all 0 failures. The ImGui drag gesture's on-screen feel is a rendering result checked by eye in the running client; its resolution rules are unit-tested.
**Hierarchy interaction model (fixed alongside §4.1's secret section):** the panel is begun with `ImGui.WindowNoMove` and re-grants movement through `builder/TitleBarWindowDrag.cs`, so the window moves **only by its title bar** and a drag in the body is free for the marquee. That is not a preference: ImGui's own "move from title bar only" switch is an `io` config the vendored addon does not expose (the same limitation `EditorChrome` documents for dock-node flags), so without it a body press could move the window instead of starting the gesture. **Each row is split in half**: the left half is the interactive item (select, drag, right-click) and the right half belongs to the marquee. This split is required, not cosmetic — `ImGui.Selectable` **auto-spans the full available width when its size is 0**, so a row item otherwise covers its whole line, and a press beside the title grabbed the row (starting a node drag) instead of starting a marquee; the addon's `SelectableSpanAvailWidth` is a stray constant (1<<24 is not a real ImGui selectable flag), so removing it changed nothing. Leaf rows are therefore sized to the left half explicitly (`Selectable(label, selected, 0, size)`), while tree rows — whose `TreeNodeEx` takes no size — are flagged `AllowOverlap` with a filler `InvisibleButton` laid over their right half (`DrawRowMarqueeZone`), a button that carries no behaviour and exists only so the press belongs to neither the row nor the window. The marquee's start test is explicit geometry (`IsMarqueePress`: inside a right-hand band, or over empty space) rather than "nothing is hovered", because the filler button is an item. The marquee's *hit* rects are still widened to the panel's right edge (`RecordRow`), so dragging a selection box across a row line still selects that row.
**Acceptance criteria:** A creator can undo and redo any edit — including a script edit made with that script selected — and reorder and reparent by dragging in the hierarchy.
**Difficulty:** 🟠 undo/redo (incl. code-editor session entries) · 🟠 hierarchy drag/reparent

*(Editor chrome, decided alongside the 2.4 work: every terminal window and builder panel is begun with `WindowNoDocking | WindowNoCollapse` — `builder/EditorChrome.cs`. ImGui's docked "maximize" gesture is a double-click on a dock node's tab bar, which hides that tab bar and leaves the panel filling the whole dockspace with no tab left to click back to normal; the addon's C# wrapper exposes no dock-node flags and no IO config, so the gesture cannot be switched off directly. With no dock node there is no tab bar to double-click, which removes it outright, and `NoCollapse` does the same for a floating window's title-bar double-click — so no window can be blown up or folded away. Cost: panels can no longer be dragged into dock splits (they stay freely movable and resizable, and their positions still persist in `user://imgui.ini`). Restoring docking while keeping the gesture disabled means patching the vendored GDExtension.)*

### Milestone 2.5 — Lighting and environment settings
- [x] Time of day (sun angle + colour), fog, and sky presets in the creation environment, replacing the fixed procedural sky (`BuilderScene.BuildViewport`). `builder/lot/LotEnvironment.cs` holds the session-only settings (`LotEnvironmentSettings`), the four presets (Day/Sunset/Night/Overcast), the pure sun math and the time-of-day **sky curve**; `BuilderScene.ApplyEnvironment` is the single writer to Godot's Environment / ProceduralSkyMaterial / DirectionalLight3D; `builder/panels/EnvironmentControls.cs` draws the editor inline in the Builder's **View → Environment** menu (no separate panel — it is a view setting, next to the wallpaper). Presets set the light/sky/fog together; the sun angle is either the manual elevation/azimuth or driven by the time-of-day clock, whichever the creator selected. Day reproduces the removed hardcoded sky exactly, so an untouched builder looks unchanged. Deliberately **not** on the undo stack and **not** marked as an unsaved lot change: it is a view setting like the camera, not an edit to the lot's objects
- [x] **The sky must actually change with the clock** (follow-up fix). Godot's `ProceduralSkyMaterial` draws its sun disc from the scene's first `DirectionalLight3D` but keeps its own four colours **static** — it has no time-of-day behaviour — so the first cut moved the sun through a fixed sky. `LotEnvironmentSettings.SkyPaletteFromTime` now keyframes the sky/ground gradient + sun colour/energy over 24h (ten stops, the 12:00 stop being the Day preset's own sky so noon stays exact) and `Effective()` substitutes them while the clock is on; the stored manual colours are never overwritten, so unticking the clock restores them. Dusk is intentionally warmer and longer than dawn (warm stops at 18:00 **and** 19:30 vs dawn's single 06:30), and the night plateau is floored so the lot stays editable at midnight. While the clock is on its sky/sun-colour widgets are greyed out, exactly like the manual angle sliders. *(`PhysicalSkyMaterial` was the alternative — a real Preetham daylight model — but it would change the Day look, has one ground colour instead of a horizon split, and makes night genuinely black; kept for a later milestone)*
- [x] Environment settings persisted as lot metadata — **done, via §4.1 + §4.2**: `LotEnvironmentSettings` is serialized into the `.lot` archive's `lot.json` next to the scene (`LotSave.Write` sets `LotDocument.Environment`) and re-applied on load (`BuilderScene.ReplaceLotFromArchive` calls `ApplyEnvironment`), so the builder and a loaded/played lot agree on lighting. A lot carrying no environment block resets to the default rather than inheriting the previous lot's sky.
**Acceptance criteria:** A creator sets time of day, fog and a sky preset in build mode and sees the same lighting when the lot is loaded and played.
**Verification:** `EnvironmentSelfTest` (39 checks: the "Day == the original fixed sky" contract, preset coherence, the time-of-day sun curve including the light-rotation sign convention, and the sky-palette curve — noon identical to Day, night dark but editable, dusk warmer for longer than dawn, plus the `Effective` snapshot contract), headless under `#if DEBUG` from `BuilderScene._Ready`; the on-screen result (sky colours, shadow direction, fog) is a rendering outcome checked by eye in the running client.
**Difficulty:** 🟠 environment controls · 🟠 persistence (via §4.1 + §4.2 — landed)
**Implementation status:** fully landed. The editor half shipped with the milestone, and the "same lighting after load/play" half completed once §4.1 + §4.2 landed: `LotEnvironmentSettings` serializes into `lot.json` and re-applies on load (see the checklist item above), so the settings survive a save/reload and a Test-mode round trip.

### Milestone 2.6 — Part surface decal system
- [x] Per-face decals: logos, signs and textures placed on a **single face** of a part. The §2.3 Texture property swaps the material for the *whole* part; this is the per-face counterpart, and it is a **scene object** (`LotObjectKind.Decal`) inserted into the part it decorates — spawned from the Toolbox's Decal section **and** the hierarchy context menu's "Insert Decal" (both need a selected host), parented to its host part, and addressable by handle like any other object (§3.3). A decal is deliberately not a primitive: no collision body, no outline hull, a shared unit `QuadMesh`, and a transform **derived** from its face/offset/scale against the host (`builder/lot/DecalMath.cs` + `LotObject.RefreshDecalTransform`, with `_EnterTree` re-deriving on attach/reparent/restore)
- [x] The decal carries its own data-driven properties through the §2.3 `LotPropertyRegistry` (face, image, offset U/V, scale U/V, opacity), so the Inspector gets the widgets with no new UI code and the Lua verbs (`SetDecalFace` / `SetDecalTexture` / `SetDecalOffset` / `SetDecalScale` / `SetDecalOpacity` / `SpawnDecal` + getters) fall out of the same declaration per §2.2. The part properties (anchored/collision group/whole-part texture) are not offered on a decal, and vice versa — `IsPart` and `IsDecal` split the declaration table
- [x] Rendering: a quad on the chosen face, offset along the face normal to avoid z-fighting (proportional lift, `DecalMath.Lift`) and **clipped by construction** — `|offset| + scale/2 <= 0.5` in face fractions, so the patch can never grow past the face edge or bleed onto a neighbour. It follows the parent when the part is moved, rotated, resized or has its own material changed, because it **is** a child: the local numbers are scale-free (the host scale is divided out and multiplied back at render), so a host resize keeps the patch at the same fraction of the face with no per-frame work
- [x] The patch is **adjustable by dragging**: with a decal selected, a drag on its host slides the image across the face (`PartDragController`'s decal slide — cursor ray meets the face plane, the grab offset is preserved, the write goes through the property descriptors and the whole drag is one "Move Decal" history entry). The face itself is switched from the Inspector dropdown or `SetDecalFace`, and the image's transparent areas stay transparent (`StandardMaterial3D` alpha transparency, unshaded)
- [x] Texture picking reuses the existing image path (`ImageFilePicker` + `LotTextureCache`, §2.3) — same magic-byte sniffing, same on-disk cache, same reference counting (`SetTexture`/`ReleaseTexture` are shared with the part texture field) — rather than a second loader
- [x] Decals serialize with the lot (`lot.json`, §4.1) as their own `"decal"` kind tag with their parent pointing at the host, and their image bytes ship in the archive's `assets/` (read through `LotVFS`, §4.1) via `LotArchiveCollect`/`LotSceneLoad`'s shared asset-id lookup — so a saved lot carries its decals and a decal never points at a file only the author has
**Acceptance criteria:** A creator inserts a decal into a part, picks a face and a texture, sees the logo on that one face only, saves the lot, and reloads it on another machine with the decal and its embedded texture intact.
**Difficulty:** 🟠 face targeting + z-fighting/clipping · 🟡 property wiring (reuses 2.3) · 🟠 persistence (via §4.1)
**Implementation status:** landed and verified headless; the on-face UI step (see below) followed in the same milestone. Implementation notes worth keeping: the face vocabulary is `+Z/-Z/+X/-X/+Y/-Y` (default +Z) with axes ordered so `u x v == normal` (a proper rotation, never a mirrored image); a non-uniformly scaled host is compensated exactly because every face axis is a signed part axis, and a *mirrored* host (negative scale component) is deliberately not compensated (documented in `DecalMath`); curved surfaces place on the bounding-box face (a `Sphere/Cylinder/Capsule` patch floats just off the curve) — true surface conform is out of scope; `SetAnchored`/`SetCanCollide`/`SetCollisionGroup` remain callable on a decal for signature safety but do nothing (no body), and the gizmo is gated off for a decal selection because its transform is derived.
**The Decal tool (follow-up fix).** The first cut could only slide a decal that had been selected in the Hierarchy first, and the face was switched from an Inspector dropdown — which read as "there is no way to move it or pick a face". Now `GizmoMode.Decal` is a first-class tool beside Select/Move/Rotate/Scale, and its click means *this face*: the raycast's surface normal names a face (`DecalMath.FaceFromNormal`), a click inside an existing panel picks it up and starts the slide, and a click on bare surface inserts a panel centred on the clicked spot (`PartDragController.HandleDecalPress` → `BuilderScene.InsertDecal(builder, host, face, offsetU, offsetV)`). A new decal opens the image browser immediately, so it is never left a blank white square. The toolbox keeps the tool switcher reachable with a decal selected, and both the toolbox and the hierarchy context menu route through the same insert path.
**On-face UI content (the user's extension of this milestone).** A decal is now a face-mounted **panel** whose `Content` chooses what it draws — `Image` (the picture patch), `Text`, `Button`, `Scrollbar` (`DecalContent` + `DecalMath.ContentNames`). Rendering is one `Label3D` and one thumb quad, both internal children of the decal (`InternalChildMeta`, invisible to the hierarchy/walk/snapshots): Text hides the quad and shows the label; Button shows the surface plus a contrast-coloured label (`DecalMath.LabelColorFor`); Scrollbar shows the track plus a thumb that rides `decal_scroll` (`DecalMath.ScrollThumbOffset`). The label is sized in the panel's own unit frame (one line = FontSize/160 of the panel height, wrapping at 90%), so text and panel scale together with the part. `Label3D` is a **deliberate borrow from Godot's 3D layer** — the in-house ImGui UI is screen-space and cannot put glyphs on a face — and it is marked as an internal implementation detail. The property system gained its `Text` kind (descriptor accessors, Inspector `InputText` field with the same one-entry-per-edit-session undo rule, capture/load/snapshot plumbing), which §5.3's lot-UI labels reuse. Lua grew `SetDecalContent`/`SetDecalText`/`SetDecalScroll`/`SetDecalFontSize` + getters. **Button and Scrollbar are visuals until in-session input routing lands**: a click reaching a script is the shared §3.7/§5.2/§5.3 blocker (player-originated interaction), so wiring it here would be the fabricated plumbing that section deliberately refuses; a script can already drive the visuals (`SetDecalText`, `SetDecalScroll`).
**Verification:** `DecalSelfTest` (100 checks, 0 failures), headless under `#if DEBUG` from `BuilderScene._Ready`: the face table and handedness, the face-from-normal and covers-point rules behind the tool, the clamps, unit and scaled-host placement math with the render round-trip, the live-host contract (attach placement, face change, clamping, riding host motion, the un-refreshed-resize property), the panel contents (which of quad/label/thumb is visible per content, text and font plumbing, thumb position, the contrast rule), the declaration split, a capture → restore with the host link / authored values / content / text / image reference intact, and every bound Lua verb driven through the real VM. Alongside it, `LotPropertySelfTest` grew its accessor check to Float and Text, and `LotArchiveSelfTest`'s kind-tag round-trip covers `"decal"` (235 checks). The on-screen result (a logo or a button sitting on one face, the slide gesture, transparency, the label's size) is a rendering outcome checked by eye in the running client, the project's usual split. **Known gaps, stated rather than implied:** a mid-session host *scale* change does not re-derive the tiny normal lift until the next refresh (the panel itself stays correct); `Secret_Asset/`-routed decal images follow the same routing rule as part textures; Button/Scrollbar take no input yet (above); the drag's grab-relative feel and the label's exact line metrics are eye-checked.


### Milestone 2.7 — Precise scale gizmo (6-handle)
*The §2.2 scale tool ported Im3d's three axis-line handles, whose drags grow the part from its center — both faces move at once, which is usable for overall sizing but cannot stretch one side precisely. This milestone gives scale its own per-face handles (the six spheres) while leaving the translate/rotate tools and the rest of the gizmo stack untouched.*
- [x] Six face handles: `+X / -X / +Y / -Y / +Z / -Z` spheres centered on the part's bounds faces, replacing the three axis-line handles; the center uniform dot (`HandleUniformScale`) stays as the "grow all axes" affordance, so the mode keeps one handle set for both overall and one-sided sizing. Mesh-less targets (a model group) keep the Im3d axis lines — there are no faces to sphere
- [x] Handle placement is bounds-relative — the spheres sit on the part's actual faces (computed from the mesh's AABB in the part's local frame, so a rotated part's handles follow its faces) — but each sphere is drawn and hit-tested at a screen-constant radius via the existing `GizmoContext.PixelsToWorldSize`, so picking is stable whether the part is tiny or building-sized. The pick bound grows to the mesh's world half-extent for meshed targets: the Im3d pick sphere only covers its own origin-local handles, and a face sphere on a large part sits far outside it
- [x] Anchored-side drag: dragging a sphere moves only that face — the axis component scales while the opposite face stays where it is, which is the precision the center drag cannot give. The offset is the cursor's in-plane motion along the projected face normal, snapped through `GizmoMath.Snap` with the §2.2 scale increment and `Alt` hold-to-invert (`GizmoController.ResolveSnap`, already resolved once per frame in `FillAppData`); the drag writes scale **and** the compensating position shift together, and the minimum-scale clamp is **`1e-4f`** (the milestone's chosen floor; the Im3d axis path keeps its own 1e-3 relative floor, pinned side by side in the self-test)
- [x] Sign conventions pinned in implementation notes next to the math: a `-X / -Y / -Z` sphere grows its own side outward (its normal is the handle's axis, not the part's), and the `FlipGizmoWhenBehind` axis flip the line handles do is deliberately **not** applied — a face handle that teleported to the far side of the part when the camera crossed the horizon would be unusable
- [x] Pick/feedback through the existing state machine: new handle ids outside today's `0-8` set (faces are `10..15`), `GizmoColors.Highlight` on hot/active, and the translation handles' fade as the face normal turns toward the viewer (`GizmoMath.Remap`) so a face you are looking straight at does not swallow its handle — floored at 0.2 alpha so a face-on sphere stays grabbable
- [x] Undo/drag lifecycle unchanged: the whole drag is still one history entry committed on release, `WantsMouse` still gates the viewport's background click, `ResetInteraction` still drops handle state on selection/tool change — a face scale restores the exact pre-drag local transform, position shift included. **Reading this contract closely found a pre-existing hole and fixed it here:** `RunGizmo` only called `UpdateDragHistory` when the frame produced a change, but a drag's LAST frame is the release frame — which reports no change — so the entry sat uncommitted until some later selection/tool change, and a following drag could fold into the previous one. The call now also runs while an entry is open (`changed || _wasDragging`), so the commit lands on release for every handle, face spheres and Im3d axes alike
**Acceptance criteria:** A creator selects a part, sees six face spheres plus the center dot, drags one sphere and stretches only that side (opposite face stays put, snap increment and `Alt` override behaving as move/rotate do), undoes the whole drag in one Ctrl+Z, and the same works on a rotated, non-uniformly scaled part without the mesh jumping.
**Difficulty:** 🟠 handle math (bounds placement, anchored-side offset, sign conventions) · 🟡 draw/hit-test reuse · 🟠 snap/undo wiring · 🟡 tests
**Implementation status:** landed and verified headless. `builder/gizmos/FaceScaleMath.cs` holds the pure math (handle ids 10..15, face axis/sign tables shared with the §2.6 decal vocabulary, mesh-bounds face centres re-derived every frame, world half extents for the pick bound, the drag arithmetic) plus `FaceScaleBehavior`, the original (non-Im3d) hot/active logic — kept out of `GizmoBehavior` so that file keeps its "readable side by side with im3d.cpp" property. `GizmoController.RunScaleGizmo` now takes a `ref position` beside the scale (the face drag shifts the origin, which is exactly what anchors the opposite face), draws the six spheres for meshed targets, and keeps the axis lines for targets without a mesh. **Two design decisions worth keeping, both discovered while implementing:** (1) the drag first measured the cursor's motion on a camera-facing plane through the press-time face centre, along the *projected* face normal, deliberately avoiding the Im3d axis-line closest-approach scheme — **the second-client fix round below supersedes that**: the plane measurement under-follows the cursor by sin²θ (half the cursor's speed at a 45° view), so the drag now uses closest approach with an explicit head-on guard, and the self-test pins both the tracking and the no-jump contract. (2) The pick bound grows to the part's world half-extent, because Im3d's pick sphere only covers handles that sit next to the origin while a face sphere sits on the surface — far outside it on a large part. Every drag frame re-derives the spheres from the live transform, so a rotated, non-uniformly scaled part's handles sit on its visual faces with no cached positions to go stale.
**Verification:** `GizmoSelfTest` grew to 228 checks (0 failures), headless under `#if DEBUG`: the face table and handle ids, bounds→face-centre derivation (unrotated, scaled, rotated 90°, non-uniform scale), the pick-bound half extents (including a 45° sliver), the projected-direction rule (face-on → zero, 45° → 45°), per-face drag arithmetic with the opposite-face-fixed contract in both directions, snap, the 1e-4 floor with its consistent shift, degenerate (zero-thickness) refusal, the behavior end to end (hover → capture → drag → hold → drag further → release with hand-checkable numbers on the +Y face), and the head-on no-jump regression. The on-screen result (sphere placement, the fade, drag feel on a rotated non-uniform part) is a rendering outcome checked by eye in the running client, the project's usual split. **Known gaps, stated rather than implied:** a mirrored (negative-scale) host is not compensated — the same declared limitation `DecalMath` carries; a camera rotated *during* a drag keeps the captured measurement line (the drag does not re-fit mid-gesture); and the axis-line handles remain for mesh-less targets rather than being replaced outright.
**First-client fix round (the drift bug).** The first cut applied the drag as `position += offset` while the offset was already the cursor's *total* movement since press, so every frame re-added it: the part ran away from the cursor ("doesn't follow the mouse, just drifts") and the runaway motion buried the scale change ("doesn't even scale"). Both outputs are now **absolute from the press-time part** — `FaceScaleBehavior` returns the press origin plus the total offset (and the absolute scale), and the controller *assigns* them — so holding the cursor still holds the part still, and dragging further tracks 1:1. The behaviour test pins it: same ray on consecutive frames must produce identical outputs, and a further drag must land on the press origin plus the new total, not the sum of the frames' offsets. *(Manual call-outs from the same round: the freecam's Ctrl-to-descend binding was removed on request — `FreecamController` now flies up on Space only — and the six face spheres were doubled on request: draw diameter `GizmoSizePixels * 4` and hit radius `GizmoSizePixels * 8`, face spheres only, so the uniform centre dot stays the distinct small affordance.)*
**Second-client fix round (the cursor-follow bug).** The balls *moved*, but slower than the pointer — "gizmo balls … dont quite follow the cursor". Root cause: the plane-projection measurement multiplied the cursor's in-plane motion by the view's sine **twice**, so the drag tracked at **sin²θ of the cursor's speed** — half speed at a 45-deg view, a quarter at 30 deg, nothing when looking straight down the face. The suite had missed it because every existing drag frame used a view perpendicular to the face normal, where sinθ = 1 and the two schemes agree exactly; the new pins close that blind spot. The drag now measures the **closest approach between the cursor ray and the face's own normal axis** (`GizmoMath.Nearest` — the scheme the ported axis handles and the Move tool already use): the ball stays under the cursor at every usable angle, perspective-correct. The milestone's no-jump contract survives as an explicit guard — a press within ~8 deg of straight down the normal (`FaceScaleMath.MinViewAlignment`, the `aligned < 0.01` refusal Im3d's translation handles carry) captures but refuses to move, latched at press like every other piece of drag state — and the captured start parameter keeps the drag grab-relative, so an off-centre grab of the ball does not jump on the first frame. `ProjectedAxisDirection` and its checks are gone (dead code, §2.3). Pinned by `GizmoSelfTest`'s new `TestFaceScaleTracking`: the 45-deg drag lands on the closest-point value (scale 2.2856507, origin (0, 0, 0.6428254)) with the old plane value (1.7071068) asserted wrong; both sides of the guard cone (7 deg refuses, 9 deg tracks); the off-centre grab (start 0.3, grab-relative scale 1.3, lateral motion contributing nothing); and every pre-existing frame number unchanged — the perpendicular-view cases are numerically identical between the two schemes. `GizmoSelfTest` now runs **246 checks, 0 failures** (was 228: −3 projected-direction checks, +4 view-alignment checks, +17 tracking checks).

### Milestone 2.9 — Part transparency & luminescence
*Two per-part surface properties that make a part read as glass or as a light: a transparency amount and a luminescence amount. Both are data-driven entries on the §2.3 `LotPropertyRegistry` table, so the Inspector widgets, the `lot.json` persistence, the §3.6 session snapshot and the undo path all fall out of the declaration — the milestone is the material wiring plus the honest decision each property carries (how transparency composes with picking and decals, and what a glowing part is allowed to cost).*
- [ ] **Transparency** — a `Float` property, 0..1, **default 0 (fully opaque)**, following the Roblox-style direction the rest of the vocabulary uses (0 = solid, 1 = invisible). Writes go through the part's material (`StandardMaterial3D` transparency mode + albedo alpha) and through `LotPropertyService` like every other property, so undo, save/load and the session restore need no per-feature code; the Inspector row and the bound Lua verbs (`SetTransparency` / `GetTransparency`, verb-first per §2.2, documented next to the binding) fall out of the same declaration.
- [ ] Transparency decisions stated rather than implied: an invisible part stays **selectable/draggable** (the §2.3 `CanCollide = false` precedent — the outline/pick mask keeps it addressable, not the renderer); `CanCollide` stays orthogonal (an invisible wall is a legitimate build); a decal on a transparent host keeps its own material (the §2.6 surface is a separate quad). Godot's transparent-pass sorting limitation is stated in the creator doc rather than papered over, and the composition rules are pinned by the self-test.
- [ ] **Luminescence** — a `Float` property, **default 0 (off)**, ≥ 0: 0 is a normal lit part; above 0 the part's material gains emission scaled by its own colour (a lamp keeps its tint) and the part contributes real light up to a **documented budget** — a real `OmniLight3D` per glowing part is a per-part cost and the forward renderer caps visible lights, so the milestone carries a stated cap (a per-lot light budget with nearest-N selection, measured by §14.1's harness) or an emission-only first cut if the measurement says so. Never an unbounded light per part. The property carries the *amount*; a separate glow colour is a possible follow-up, not part of this milestone.
- [ ] Bound Lua access (`SetLuminescence` / `GetLuminescence`) + the registry declaration, documented next to the binding per §2.2; both properties ride the standard write paths (Inspector edit, script write, save/load, session restore, undo) with no second implementation.
**Acceptance criteria:** A creator builds a glass pane and a glowing lamp out of ordinary parts, sees both live in the editor, sets both from a script, saves the lot and reloads it with both intact; an untouched part (both values 0) renders exactly the pre-milestone opaque/unlit part.
**Difficulty:** 🟠 material wiring + the transparency edge cases (picking, decals, sorting) · 🟡 registry/Lua/persistence (data-driven — §2.3 does the work) · 🟠 the luminescence light budget (the only genuinely new runtime cost)

  - Known cosmetic quirk: a drag dropped near the secret section draws its insertion line inside that section, but the landing is resolved against the node's *real* parent (`LotRoot`) because the section is a view, not a container — so a drop can never move something *into* secret content. Not fixed, deliberately: fixing it means teaching the drop feedback about the section for no behavioural gain.
- [x] Introduce **`LotVFS`** — a Virtual File System that **streams assets directly out of an open `.lot` archive without extracting them to disk**. Primitives: Godot's `ZipReader` (`Open` → `FileExists` / `GetFiles` / `ReadFile`) to read and `ZipPacker` to write; the archive index is read once and entry bytes are handed straight to Godot's **buffer** loaders — `Image` `Load*FromBuffer` for textures (the path 2.3's `LotTextureCache` already uses), `GltfDocument.AppendFromBuffer` + `GltfState` for models (§7.2), and the matching buffer path for audio (§8.2). `LotVFS` is the **single read path** for every asset consumer, so there is one loader and one disposal rule. Tier note: this is **Godot-infrastructure-facing** code — it owns file/zip/buffer access and exposes only narrow, verb-first accessors (`OpenLot`, `ReadEntry`, `TryReadAsset`) upward; Lua never touches it directly (§1.1).
- [x] Versioning + migration: a `formatVersion` in `manifest.json`; an older file is either migrated or rejected with a clear, readable error — never a silent half-load. Document the migration step for every bump.
- [x] **Autosave and crash recovery** (moved here from §2.4 — there was nothing to serialize until this format existed): a periodic autosave to **`user://autosave.lot`**, a crash marker written on unclean exit, and a recovery prompt on boot that offers the recovery file over the last manual save. Autosave rides the same writer as a manual save (§4.2), so it can never emit a file the loader rejects. **The prompt now actually loads the snapshot** (it used to only keep the file and point at the File menu, which was true while §4.2 was unbuilt): `Recover` runs the same `LotLoad` path Open Lot… does, but **does not adopt the snapshot's path as the lot's file** — a recovered lot has no destination the creator chose, so it is marked dirty (quitting warns, `Ctrl+S` asks for a file) and the snapshot is deleted **only after a save that actually succeeded** (`Builder.WriteLot`), so a failed or cancelled save can never destroy the only copy. The load is deferred to the top of the next layout pass rather than run where the modal is drawn, because the modal renders *after* the panels have walked the scene and replacing the lot there would free nodes they had just read. **Flagged by the post-3.11 review — not yet optimized:** the periodic write is synchronous on the main thread, so a large lot can hitch at the save instant; measure the hitch (§14.1's workload) before any fix — moving the write off-thread means reworking `LotArchiveIo`'s Godot-`ZipPacker` half, so it is a deliberate decision, not a guess.
**Window close is routed through the unsaved-changes prompt (follow-up fix).** Clicking the OS window's X used to let Godot quit immediately, which bypassed the unsaved-changes prompt *and* — because the scene tree is still torn down — ran `_ExitTree`, cleared the crash marker and so made an abandoned session look "clean", suppressing the recovery prompt as well. `Builder` now sets `GetTree().AutoAcceptQuit = false` in `_Ready`, handles `NOTIFICATION_WM_CLOSE_REQUEST` (ignored while the unsaved-changes prompt is already up, so a second X click cannot discard the work being asked about), and hands `AutoAcceptQuit` back in `_ExitTree` so the terminal keeps Godot's default. X therefore means "close OpenLot" (`RequestQuit(true)` → `QuitApplication`), not "go back to the main menu", which is what the menu's Exit does. Two related data-loss bugs in the same path were fixed with it: the prompt's **"Save & Quit" only cleared the dirty flag and never wrote a file** (a 2.3-era stub) — it now saves through the real pipeline, parking the quit intent in `_quitAfterSave` so a save that still needs a destination from the file dialog can finish first, and a **failed** save cancels the quit rather than ending the session on top of it; and the pause menu's "Save Lot" button, which still printed "persistence lands with milestone 2.3", now calls the real save.
**Acceptance criteria:** The `.lot` format is documented and versioned, a file written by an older build is either migrated or rejected with a clear error rather than failing silently, a lot is recoverable after a crash or restart without losing work, and an asset loads from inside the archive with no extracted copy left on disk.

### Milestone 3.6 — Constraints and joints
- [x] Hinge and weld constraints between parts, requiring dynamic bodies (parts were static-only)
- [x] Decide how constraints interact with Anchored / CanCollide from §2.3
**Acceptance criteria:** A creator hinges or welds two parts and they hold or pivot correctly in play.
**Implementation status:** landed and verified headless, on the lightweight design agreed for this milestone. Two link kinds only — beyond the §2.3 Texture/Anchored set those are the vocabulary: `builder/lot/LotConstraint.cs` owns the model (a weld or hinge record between two part handles, a hinge's pivot stored part-local, its world-second-side form, the id table and the `constraints` block of `lot.json`), the **Roblox anchor rule** (one anchored part freezes its welded island; the weld that would join two anchored islands goes inactive — deterministic in creation order, so it is replayable) and the JSON shape. `builder/lot/LotConstraintSession.cs` is the dynamic-body layer and joint builder: unanchored parts swap `StaticBody3D` → `RigidBody3D` on session entry (via `LotObject.SetSimulated`, mass from the mesh's volume) and back on exit, and each active record becomes a Godot joint — welds a `Generic6DofJoint3D` with all six axes locked (enabled limit, lower == upper == 0 — Godot has no locked switch), hinges a `HingeJoint3D` whose frame aims its local Z at the chosen world axis, both added as **siblings of the parts they constrain** (a joint parented to a body it links is how half-frozen axes happen). **A simulated body lives at the lot root, not under its part** (`SetSimulated(simulated, host)`), and `SyncVisuals` puppets the part from the body once per physics step — physics owns the body, the part follows it, exactly the capsule controller's visual/body split. The first cut nested the body under the part and never synced, so bodies fell invisibly while the mesh stood still ("unanchored objects are not affected by gravity" reported from the client); the entity-destroy walk now also releases a simulated body explicitly (`ReleaseSimulatedBody`), since it no longer dies with its part. Anchored parts deliberately keep their static body — infinite mass by definition, so the solver never sees them — and the player capsule is excluded outright, since its controller owns it. **The session build hangs off `EnterTestMode`, not off `StartScriptRuntime`** — the script runtime early-returns when Lua is unavailable, and the body swap and joints are physics, so they must exist even with a dead scripting layer. Joints are session artifacts, marked `InternalChildMeta`, rebuilt idempotently whenever a script reload mid-session changes the tree and freed by the entity-destroy walk the moment a linked part dies (a joint to a freed body is a crash). The editor is the same data: Toolbox **Weld**/**Hinge** buttons run a picker (`builder/gizmos/ConstraintPicker.cs`). Weld is two clicks (part, part). Hinge is: click the first part, click the second part or empty space for the world, then a **placement step** — a visible hinge-point marker (ball + axis rod, internal-marked) appears at the first click's point, further clicks move it (on a surface, or along the camera-facing plane on empty space), and the Toolbox's **Confirm**/**Cancel** buttons finish or abandon it; nothing is created until Confirm. A fresh hinge gets the **swing-friendly default axis** — horizontal, perpendicular to the line between the parts (`ConstraintPicker.DefaultHingeAxis`), because the vertical axis' zero-torque equilibrium reads as "the hinge does nothing" — and the axis rod shows it before Confirm. **The axis is a free world-space direction with sharp tools** (`builder/gizmos/HingeAxisMath.cs`: exact **Vertical**/**Horizontal** presets and 45° **Tilt**/**Yaw** steps), offered both during placement (Toolbox) and afterwards (Inspector, one history entry per press), and **a hinge marker is drawn for the selected part's hinges in build mode too** (`builder/gizmos/HingeVisualizer.cs`, pooled internal-marked markers via the shared `ConstraintVisuals`) — which is what makes an orientation, and a change to it, visible without entering Test mode. The axis persists as a v1 letter when it is axis-aligned ("x", "-y", ...) and as a vector otherwise, so old lots and angled hinges both read. Each gesture is one undo entry. The Inspector grows a Constraints section (`builder/panels/ConstraintControls.cs`) with per-link enable/remove and hinge axis/limits/motor widgets, live-applied to the running joint, and welds/hinges are **listed in the Hierarchy** under a `Links (n)` section (`HierarchyPanel.DrawLinksSection`): one row per record, click selects the first part (whose Inspector edits the link), right-click offers Select parts / Toggle / Remove — drawn as a view over the one record table (the same pattern as the base-content section), not as duplicated placeholder nodes that could drift. **Test mode is an instance of the lot** (the §3.4 semantics completed): entering snapshots the authored world (`builder/lot/LotSessionSnapshot.cs` — transforms, colors, visibility and every declared property per entity, UI rects/labels, held texture ids, the constraint and collision-group tables, and the entity set) and leaving restores it after the exit reload, so physics results, script edits and session-spawned nodes cannot leak into the build lot or a later save. Not restored, deliberately: an authored entity a session script *destroyed* (Test mode restores state, not deletions), the camera and the selection. Scripts get eight verbs on the existing bound surface: `WeldParts`, `Unweld`, `IsWelded`, `CreateHinge`, `SetHingeLimits`, `SetHingeMotor`, `SetHingeAxis` (aim the axis at any direction; the string form on `CreateHinge` only spells the six axis directions), `RemoveConstraint`. Reserved and rejected with a readable message rather than half-supported: the servo/angle motor mode (waits on §3.8's tick drive), restitution and break thresholds (waits on §3.7's events). **Long chains warn instead of capping** (the agreed decision): a session counts the active links per welded island and warns above eight (`LotConstraints.ChainWarnThreshold`) — springiness grows with chain length, and the fix (anchor a root, split the build) stays the creator's call. The hinge editor also gave the property system its `Float` kind (decision D3), which §3.11's mass/friction will reuse. **Manual call-out:** `LotObject.CollisionBody` is now typed `PhysicsBody3D` (base of both bodies) instead of `StaticBody3D` — every existing reader compiles unchanged, but anyone who typed it `StaticBody3D` in their own code must widen it too.

### Milestone 3.12a — Account identity primitive
*The decentralized account (design doc `docs/design/milestone-3.12a-account-identity.md`): a locally generated P-256 keypair whose 50-character key string IS the account. - [x] 50-char key string: `version(1) + seed(32) + SHA-256 checksum(4)` → base64url, exactly 50 characters; a mistyped character is refused by the checksum with a readable message, never silently decoded into a different account
- [x] Public **Account ID** (22-char, domain-separated truncated hash of the public key) — what games store and compare; the 65-byte public key travels in the handshake; the private half never leaves the client
- [x] Challenge-response primitive (`AccountKey` + `AccountChallenge`): `OPENLOT-AUTH-v1`, bound to the lot, a fresh nonce and an expiry — a captured signature is useless on any other host or session (replay rejection pinned by the suite)
- [x] Key foundation pinned by the seed-only-import spike: **P-256 ECDSA via the .NET BCL** — a keypair rebuilds from its 32-byte seed alone on the runtimes the game targets, zero new dependencies (Ed25519/NSec recorded as the fallback candidate, not taken)
- [x] The §1.1 boundary extends to the key: signing is a fixed-schema core operation; no bound Lua method exposes the seed, the key string or a signing operation (suite tripwire over all 121 bound methods)
- [x] Local storage (`user://account.cfg`, path-explicit so tests drive scratch files) + terminal flows: `register <name>` (create + one-time reveal), `login` (unlock), `login <key> [name]` (import), `logout` (lock); register/import refuse to clobber an existing account file; the §5.1 Unity-parity semantics change is deliberate and flagged there

**Verification:** `CameraSelfTest` — 21 synchronous checks (8 new: the blend endpoints/midpoint, smoothstep, and the glide's exact snap / zero-delta / monotone approach / exact landing; plus 4 aim-guard checks, see the fix note below) + a 27-check staged probe (12 new, across a second session): six wheel notches in settle at exactly `ZoomMin` with the pose at the eye (`< 0.01` m) and the mesh faded (≥ 0.95); six notches out land **exactly** on `DefaultDistance` with the authored transparency restored; a fixed camera ignores the wheel; a script-set first person pins fully in and a wheel-out takes the view back; the offset glide settles with the fade gone; the session exit resets mode/distance and returns the freecam. Full headless run: 1,954 checks, 0 failures (1,949 before the aim-guard fix; +4 synchronous +1 probe). The on-screen feel (glide speed, the fade's look) is an eye-check, the project's usual split.
**Post-milestone fix (the straight-down aim — found by the Section 5 code-health audit):** a fixed or scripted camera aiming exactly straight down or up made Godot's `Node3D.LookAt` log "Target and up vectors are colinear" **every frame** (304 occurrences in one suite run, pose still the engine's arbitrary fallback). All four aim sites (`Fixed`, the zoom blend, `Scripted` shots, the orbit) now go through one `OrbitalCamera.AimAt` → `LotCameraMath.LookBasis` — a verbatim port of `Basis::looking_at`'s math including the `Vector3::get_any_perpendicular` fallback — so every ordinary pose is byte-identical to `LookAt` and the colinear pose is the engine-identical basis **without** the per-frame warning. `CameraSelfTest` pins both halves against the engine's own output: non-colinear vs the managed `Basis.LookingAt` (identical), colinear vs the native `Node3D.LookAt` path — which also recorded that the managed static **throws** `ArgumentException` on colinear input (so it cannot be the reference; nothing in the codebase used it). Deliberate cost: the two colinear reference calls invoke the engine's warning once each per run — the proof itself is the only colinear warning left in the log.
**Acceptance criteria:** A player wheels from the full orbit down to the eye and the view blends into first person smoothly (mesh fading out, no snap), wheels back out and lands exactly on the previous orbit; a scripted camera is zoom-proof; the same values move after a rebind.

### Milestone 5.6 — Tiling window modes (Hyprland-style)
*Windows are free-floating today. Docking was deliberately turned off (`EditorChrome`) because the dock-node double-click "maximize" gesture cannot be disabled from the wrapper, and the accepted cost was "panels can no longer be dragged into dock splits". This milestone gives that arrangement back without re-enabling docking: OpenLot computes every tile itself each layout pass and hands windows their rect via `SetNextWindowPos` / `SetNextWindowSize` (`CondAlways`), so the broken gesture cannot return and the vendored GDExtension needs no patch. The headline arrangement is **viewport focus** — the 3D view owns the master tile so most of the screen is the scene, with the panels stacked along the edge — plus Hyprland's signature gaps and focus border riding on §5.4's window-style service.*
- [ ] Global mode toggle — **Floating** (today: windows drag, resize and persist geometry in `user://imgui.ini`) ↔ **Tiled** (the layout owns geometry; windows run `NoMove` / `NoResize` while tiled and `TitleBarWindowDrag` is bypassed rather than allowed to fight the computed rect). The bottom command strip (`BuilderCommandLine`) is not a tile — it keeps its fixed full-width slot
- [ ] Per-window float toggle (the `togglefloating` equivalent): any single window can pop back to floating while the rest stay tiled, from the View menu — and from the window itself if a title-bar affordance proves clean, since `WindowNoCollapse` already spends the title-bar double-click on nothing
- [ ] Layout presets — at minimum **Viewport focus** (master = the 3D viewport at a default ~0.7 ratio; secondary column = Toolbox / Inspector / Hierarchy / Output, plus the Code Editor when open) and an even two-column split; the master ratio is adjustable by dragging the tile divider, which is the standard resize gesture because window grips are off in tiled mode
- [ ] Hyprland-flavoured trimmings on top of §5.4: gaps between tiles (size setting, 0 = off), rounded corners and border size/colour from the shared window-style set, plus a focus-coloured border on the active tile
- [ ] Applies to builder panels and terminal windows alike (`Builder.DrawLayout` and `Terminal.OnLayout` resolve the same layout); modals, dialogs and file pickers never tile — they stay floating above the layout — and the wallpaper's under-dockspace window is untouched
- [ ] **Floating geometry survives a tiled stint**: tiled rects must not overwrite the remembered floating positions (e.g. tiles run `WindowNoSavedSettings` while tiled so the last floating rect stays in `imgui.ini`); toggling back finds windows where they were, not in their tiles
- [ ] Tiling is client preference, never lot state: mode, preset, gap and per-window float flags persist in a `[layout]` section of `user://openlot_settings.cfg` beside §5.4's blocks. Deliberately out of scope in the first cut: animated tile transitions (instant geometry per frame) and keyboard-driven tiling commands (that would be §5.5 territory if ever wanted)
- [ ] Game mode is untouched (its viewport is already fullscreen and the editor chrome is not drawn), and the standing interactions must work as well tiled as floating: the hierarchy's marquee and drag-drop, the viewport's click-claiming, and the 3D `SubViewport` following its computed tile size the same way it follows a manual resize today
**Acceptance criteria:** A creator toggles tiling on, the viewport takes most of the screen with the panels tiled around it, drags the divider to rebalance, floats one window back out, toggles everything back to floating and finds the free positions exactly as they were, and the choices survive a restart.
**Difficulty:** 🟠 layout engine + gesture interplay · 🟡 presets / gaps / persistence
**Verification:** the layout math (per-preset rect derivation, master ratio, gap application, float bookkeeping) as a headless self-test in the `*SelfTest` pattern — pure geometry, fully testable without eyes; the on-screen feel (gaps, focus border, divider drag) is a rendering outcome checked by eye in the running client, the project's usual split.

## 10. Networking

*Transport baseline — research pass, Oct 2026, pinned to **Godot 4.7.2 (.NET)** (4.6/4.7 shipped no networking headline changes; these APIs are the stable 4.x surface). Full record: `docs/design/milestone-10-transport-strategy.md`.*
* **Tamed — borrowed as infrastructure (§1.1):** ENet transport with connection lifecycle and Godot-managed peer ids (`ENetMultiplayerPeer`; server id 1, the convention `LoopbackTransport` already uses) plus the low-level wrappers (`ENetConnection`/`ENetPacketPeer`); **raw byte packets without RPCs** (`SceneMultiplayer.send_bytes` out, the `peer_packet` signal in, or manual polling with `SceneTree.multiplayer_poll = false`); transfer modes and channels; per-peer RTT/packet-loss statistics, timeouts, bandwidth limits, throttling; **optional DTLS** (`ENetMultiplayerPeer.host.dtls_server_setup` / `dtls_client_setup` with TLSOptions + certificates); **UPnP** port mapping (blocking — thread it); **WebSocket** transport with TLS (the browser path); **WebRTC** (built in for web exports only — native needs the official `webrtc-native` GDExtension, a dependency not taken); dedicated-server export (`dedicated_server` tag ⇒ `--headless`, resource stripping); `OS.read_string_from_stdin()` (blocking — thread it); ENet mesh (`create_mesh`/`add_mesh_peer`) for direct peer links.
* **Built — ours, because Godot ships no service:** the `net.*` router + wire codec (§3.2, landed); the replication channel and snapshots (§10.6); session content delivery and late-join state (§10.7); rendezvous, hole punching, discovery, relay (§10.2 — Godot ships primitives only: `ENetConnection.socket_send` is documented *for* NAT hole punching, needs a STUN-derived endpoint, and **never works behind a symmetric NAT**; the engine-level P2P-across-NAT request was closed as solved by shipping UPnP); join gating, kick/ban primitives, resilience (§10.8); transport security policy (§10.9); simulation ownership and data subservers (§10.10); private/authorized hosting (§10.11); content protection (§10.12).
* **Facts to design around:** no STUN client, no rendezvous/lobby/relay in the engine; **no engine-level signal handling** (SIGINT/SIGTERM proposal open — servers treat kills as survivable, §10.5); the raw receive path **cannot report the ENet channel** (godot-proposals #12907) so OpenLot frames carry their own message-kind byte; the high-level protocol is "an implementation detail" (fine — both ends are ours, §10.1 version-gates; our wire format stays the router's); Godot's `Crypto` is asymmetric-only, so archive cryptography is .NET-side by design (§10.12).
* **Suggested execution order:** 10.1 → 10.7 → 10.5 → 10.3 → 10.2 Tier A → 10.8 → 10.9 → 10.6 → 10.10 → 10.11 → 10.12 → 10.2 Tier B/C → 10.4.

### Milestone 10.1 — Transport layer & connection lifecycle
*The physical layer of every networked session: a real transport behind the §3.2 seam, a version-gated handshake, and the host/join/leave flow. The router does not change — it already treats the transport as a seam; this milestone widens that seam and gives it an implementation.*
- [ ] **Decision record first** (`docs/design/milestone-10-transport-strategy.md` is the baseline; §10.1 extends it): transport route — **`ENetMultiplayerPeer` + raw packets as the primary** (Godot manages connect timeouts, peer ids and auth hooks; DTLS stays reachable through the host connection), `ENetConnection`-direct reserved for the §10.2 mesh/punch paths where `service()` delivers channels and `socket_send` is the punching primitive; OpenLot frame layout (message-kind byte — see the baseline's #12907 note); MTU and size guards; peer-id rules
- [ ] **`INetTransport` v2** (`builder/net/NetTransport.cs`): send class (reliable / unreliable / unreliable-ordered) + channel hint, connection lifecycle events (peer connected / disconnected / connection failed), peer enumeration with RTT/loss stats, `Kick(peerId, reason)`. The `NetRouter` call surface is unchanged; `LoopbackTransport` is updated to the v2 contract; `NetSelfTest` grows to pin it
- [ ] **`EnetTransport`**: server/client over Godot ENet — `local_port` for later hole punching, bind IP, bandwidth limits, per-peer timeouts, serviced once per session tick; unreliable sends size-guarded
- [ ] **Handshake & version gate**: magic + protocol version + lot identity hash + player display name + account identity (Account ID + a signature over the session challenge, §3.12a — no secret crosses the wire); a mismatch is refused with a readable reason (never a half-join); `maxPlayers` and the entry script come from `manifest.json` (§4.1)
- [ ] **Session flow**: `openlot host` / `openlot join <address>` / leave on the terminal surface; host-authoritative defaults; Test mode keeps `LoopbackTransport` unchanged; "list" is LAN discovery (§10.2 Tier A) and provider listings (§15) — no engine-global list is invented here
- [ ] **Verification & the naive first sync**: a two-process headless integration test (real ENet over `127.0.0.1`) plus a `SimulatedTransport` wrapper (deterministic delay/jitter/loss) that §10.6 reuses; naive entity-transform sync at a fixed rate lands here so the acceptance below is testable (the deliberate scaling pass is §10.6)
**Acceptance criteria:** Two clients join the same hosted lot over the real transport and see each other's entities move; a version-mismatched or full session is refused with a clear message; Test mode and every existing headless suite stay green.
**Difficulty:** 🟠 transport + seam · 🟠 handshake/versioning · 🟠 session flow *(research pass done — the remaining genuine uncertainty is real-world NAT coverage, §10.2 Tier B, and interpolation feel, §11.4's check)*

### Milestone 10.2 — Self-hosting & discoverability (NAT tiers)
*The free/default hosting path, split into tiers with honest reach: hosting never requires a Provider, and each tier names exactly what it can and cannot reach.*
- [ ] **Tier A — zero infrastructure (MLP-eligible):** direct `host:port` join, LAN discovery (a UDP beacon carrying lot name / player count / password flag), and a threaded **UPnP** port-mapping attempt (discovery can block for seconds; refresh the mapping; a failure is a readable message, never a hang)
- [ ] **Tier B — rendezvous + hole punching (post-MLP), split into four pieces:**
  - [ ] **B1 — rendezvous service** (self-hostable): host registration, match codes, introductions, expiry. The server side is a registry + introduction relay — the Fika reference implementation is ~150 lines of C#; ours is comparable plus tests, and it is exercisable headlessly (three loopback peers)
  - [ ] **B2 — NAT probe & classification:** RFC 5780-style mapping/filtering tests run against **our own rendezvous** (multi-socket observation — no public STUN dependency), so the client can say *why* a connection will or will not work (cone vs symmetric) instead of just failing
  - [ ] **B3 — punch engine:** both sides spray probes through `ENetConnection.socket_send`, keepalives hold the hole open, a timeout promotes the link or fails cleanly. Expectations stated honestly from real-world measurement (IMC '26 / ProbeLab, 2026): **~80% success on port-restricted-cone NATs, ~40% on symmetric, 70–83% aggregate**. Port prediction / birthday-paradox spraying for hard NATs is an **optional best-effort bonus, never a promise**
  - [ ] **B4 — NAT lab:** a userspace cone/symmetric NAT emulator (proxying UDP with per-destination mapping rules) so the punch logic is regression-tested headlessly, plus a two-network manual checklist for real-world verification (the project's usual "checked by hand" split)
- [ ] **Tier C — relay fallback (post-MLP, ties §15):** a relay for what Tier B cannot beat (provider- or community-hosted); the UI says when a session is running relayed, because latency honesty is part of the feature. A second thing the relay buys, kept on purpose: **relayed traffic hides the host's IP** (Valve runs all Steam traffic relayed for exactly this reason) — and a ready-made "tunnel service" (playit.gg-style) is the someone-else-runs-it version of this tier
- [ ] **Mesh note:** `create_mesh`/`add_mesh_peer` is the toolbox for later direct client-to-client links (§10.3's direct private chat); it is not the star session's transport
**Acceptance criteria:** A host behind a typical home router is joinable by a friend (Tier A over LAN or a forwarded port; Tier B via match code when the NATs cooperate); every unsupported case produces a specific, readable explanation instead of a hang.
**Difficulty:** 🟠 Tier A · 🟠 Tier B (B1 rendezvous · B2 NAT probe · B3 punch engine · B4 NAT lab) · 🟠 Tier C relay · 🟡 upkeep once built · ⛔️ port prediction = optional best-effort bonus, not a promise

### Milestone 10.5 — Headless lot-server runner (dedicated host)
*The `--lot <path>` runtime (bootstrapping moved here from §10.1) is the seed; this milestone turns it into a server you can operate: one command, no window, no ImGui, no viewport nodes — physics, events, timers, `net.*` and `ScriptRuntime.Tick` only — packaged for the two server targets and survivable unattended. The visual SSH host setup (§10.4) deploys exactly this artifact.*
- [ ] `openlot-server --lot <path> [--port N] [--max-players N] [--log <file>] [--quiet|--verbose]`, with env overrides; opens the archive through `LotVFS` (§4.1), reads `manifest.json` for `maxPlayers` and the **entry script**, runs that script as the lot root, and joins the session as host; `maxPlayers` is never a hardcoded cap — and `--check` validates an archive and exits (a CI/deploy gate). **The `--lot` bootstrapping moved here from §10.1** — it is runner behaviour
- [ ] **Export facts:** the dedicated-server export mode (`dedicated_server` feature tag) forces `--headless` and strips unneeded resources; `application/run/flush_stdout_on_print` is enabled so journald/Docker capture logs unbuffered
- [ ] The no-UI guarantee is held by construction and pinned by a check: a headless boot creates no dockspace/viewport/camera nodes and no ImGui — only physics, the `net.*` router, the event/tween schedulers and `ScriptRuntime.Tick` run (kept as a server-side regression, since the guarantee is defined here)
- [ ] Lifecycle: **clean shutdown is best-effort, stated rather than assumed** — the engine does not deliver SIGINT/SIGTERM to game code (godot-proposals #1361 open), so the runner tries a .NET-level signal shim (candidate: `PosixSignalRegistration` / `Console.CancelKeyPress`; verified here) for the graceful path with a readable reason to players, and documents the fallback: the boot path is idempotent and the §4.1 crash marker + autosave make a hard supervisor kill safe; a failed `.lot` boot exits non-zero with the reason on stderr
- [ ] Console & observability: a stdin command loop — `status` (uptime, players, tick rate, memory), `players`, `kick <peer>`, `stop` — plus periodic one-line status at a configurable interval; the same lines go to a timestamped log file with the §5.8 severity vocabulary (text output only — no ImGui in a server). Console input is `OS.read_string_from_stdin()` on a dedicated thread (blocking by design); the engine's known platform rough edges are documented and Linux is the guaranteed target
- [ ] Ops kit in the docs: a `systemd` unit example and a minimal `Dockerfile`, both launching the runner against a mounted `.lot`; restart behaviour documented (the durable half is §3.12's player data + the §4.1 autosave conventions)
- [ ] Packaging: Linux x86_64 and Linux arm64 server archives from the same export pipeline as the client; the §19 guide grows a "run a server" page and the §14 harness measures the runner
- [ ] Verification: a headless integration test boots a real `.lot`, connects two clients (loopback first, the real transport once it lands), observes a scripted server-authoritative action, then kills the server mid-session and restarts it without corrupting the lot — plus a ramped bot load test (up to the configured `maxPlayers`) that reports the real ceiling in measured budget units — tick ms against the frame budget, bandwidth in kbit/s per player, memory in MB per player — because RAM is rarely the wall

**Difficulty:** 🟠 boot path + console · 🟠 ops/packaging · ⛔️ rides §10.1

### Milestone 10.6 — Replication scaling: snapshots, interest management & player-owned movement
*A host for "many players in a world" is a relay and a registry, not a streamer: replication is positions and events — a few kbit/s per player — so what limits the player count is the accidental cost of the naive design, not the medium. This milestone is the deliberate scaling pass over §10.1's state sync, removing the two big accidental costs and adding the standard levers. Design doc before code (the §3.2 bar): the movement-authority choice is a trust decision as much as a netcode one. (Reference, not mechanism: Godot's own `MultiplayerSynchronizer` does per-peer visibility filtering with 1350-byte sync packets — the same idea and a copyable number; the handle-based path stays ours.)*
- [ ] **The high-frequency channel is not `net.*`:** snapshots and movement ride their own message kind with their own budgets — the router's 120 calls/s and 64 KB/s per peer must never throttle replication. Delivery class is per message (unreliable for transforms, reliable for state milestones), frames stay under the safe MTU (unreliable fragments are not a plan), and demux rides OpenLot's own message-kind byte because raw receive cannot report the ENet channel (godot-proposals #12907; if this path goes `ENetConnection`-direct, `service()` hands the channel over)
- [ ] **Player-owned movement, host-validated:** a player's own capsule is simulated on their client and replicated to the host (position/velocity at a configurable rate); the host relays it and runs cheap validation — speed/bounds clamps, teleport rejection. Result: the host does not run a physics body per player, dropping its per-player cost from "a simulated body" to "a session + a message stream". **Trust default (decided):** client-authoritative is the default — cheap hosting, and movement cheats on a private instance hurt no one; host clamps are opt-in per lot. Enforcement stays host-side per §1.3 for anything with real stakes; anti-cheat depth beyond clamping is policy/plugin territory, and the full ownership matrix is §10.10's
- [ ] **Batched, delta-encoded snapshots:** one aggregated state packet per receiver per tick instead of per-change fan-out — changed fields only, positions/rotations quantized (16-bit fixed point), sizes held to the `NetSerializer` budgets; clients interpolate between snapshots. (`net.*` stays the creator API for gameplay events; this is the high-frequency channel beneath it.)
- [ ] **Remote-player presentation (interpolation):** snapshots are rendered on a delay of ≈ 3× the send interval (Gaffer's measured rule: 10 Hz ⇒ 300 ms; **20–30 Hz ⇒ 150–300 ms**; jitter adds a frame or two), so the send rate is chosen against the delay budget rather than by taste; extrapolation stays short and mostly-linear (50–250 ms) because physics mispredicts. Tuned with `SimulatedTransport`, not eyeballed
- [ ] **Interest management:** a spatial grid decides what each receiver hears about — near players/objects at full rate, distant ones throttled or culled — with the update budget spent by priority. Per-lot configurable: a tiny arena may switch it off; a large map at 100 players is unplayable without it
- [ ] **Host-side world cost control:** let idle physics islands sleep, skip simulating what no player can observe, and make the threading decision measured (physics on a separate thread / Jolt job threads) rather than assumed
- [ ] **Measured, not felt:** `ENetPacketPeer` RTT/packet-loss statistics feed §10.5's load-test table and a debug overlay, so "acceptable sync" has numbers
- [ ] **Verification:** §10.5's load test is the yardstick — same machine, same lot, each lever measured on and off; the acceptance is the reported table (host tick ms, kbit/s per player, MB per player), not a vibe
**Acceptance criteria:** On the same hardware and lot, the ramped load test sustains a materially higher player count than the pre-milestone design with the host tick under budget and bandwidth under the uplink — and the movement-authority trade-off (what the host trusts, what it clamps, what it refuses) is written down.
**Difficulty:** 🟠 snapshots + interpolation (the measured 3×-send-interval rule above) · 🟠 optional host clamps & correction — opt-in per lot, the only path that inherits reconciliation (the client-authoritative default has none) · 🟠 interest management · 🟡 tuning via `SimulatedTransport` · out of scope v1: lag compensation/rewind · ⛔️ rides §10.1 (re-runs §10.5's load test)

### Milestone 10.7 — Session content & late-join flow
*The joining client must have the lot before it can run it — and a joiner who arrives after start must have the world, not just the events. This closes §3.2's known gap ("late joiners miss events and world state until §10").*
- [ ] **Join fast path:** when the client already holds the identical lot (content hash from §10.1's handshake), nothing transfers — peer and host agree and the join proceeds
- [ ] **Content transfer (slow path):** otherwise the host streams the archive (chunked over the reliable channel, hash-verified, resumable across a dropped connection, never executed partially). The client caches what it received under `user://` — **ciphertext only for protected lots (§10.12)**; host-scope entries (§10.10) are never part of what a client receives
- [ ] **Late-join world snapshot:** before input is enabled, the host sends the current world (entities, transforms, visibility, declared properties, UI rects, constraint and collision-group tables) — the §3.6 `LotSessionSnapshot` machinery is the seed — then normal deltas take over
- [ ] **Failure paths are readable, never half-loaded:** incompatible build, corrupt transfer, host in a non-joinable state (editing); each names the reason and the fix
**Acceptance criteria:** A fresh client with none of the assets joins a hosted lot, receives and loads it, and sees the same world the host sees — a late joiner the same.
**Difficulty:** 🟠 transfer + snapshot, riding §4.1/§3.6

### Milestone 10.8 — Session resilience & enforcement primitives
*Enforcement stays narrow and host-authoritative (§1.3); policy is plugin territory. This milestone gives the session the levers every multiplayer product needs and the failure modes readable names.*
- [ ] **Kick / ban / query** as narrow core primitives (§1.3), host-authoritative, with the reason propagated to the client's notice (the §6.2 pause/leave surface); who/when/why stays policy, never baked in
- [ ] **Refusal modes, all readable:** full, banned, wrong build, password-gated — the handshake reports which
- [ ] **Timeout & drop handling:** ENet's per-peer timeouts are the floor; a dropped client is noticed and released; disconnect reasons surface in the UI
- [ ] **Rejoin policy:** a dropped client rejoins as a fresh join + §10.7 snapshot (cheap now); a host loss ends the session cleanly with a notice — **host migration is out of scope** unless a later decision adds it
**Acceptance criteria:** Kick works with a reason; a full/banned/mismatched session refuses readably; a dropped client can rejoin without restarting the host; a host loss ends sessions with a notice.
**Difficulty:** 🟠

### Milestone 10.9 — Transport security & trust model
*Design doc before code (the §3.2 bar): what the transport defends, what it explicitly does not, and what a session's trust defaults are.*
- [ ] **Threat model written down, with non-claims:** no client trust for anything with stakes; anti-cheat depth is policy/plugin (§1.3); the client engine is open source (OpenLot is), so obfuscation is not a strategy
- [ ] **Join gating:** password/token; the SceneMultiplayer auth hooks (`auth_callback` / `complete_auth`) are a candidate mechanism, decided in the doc
- [ ] **Encryption decision: DTLS opt-in for v1** (`ENetMultiplayerPeer.host.dtls_server_setup` / `dtls_client_setup` with TLSOptions — self-signed or own-CA certs, client pinning) and **default-on once the certificate UX is settled**; plaintext sessions are labelled as such. Per-lot content encryption is a separate axis — §10.12's open-default presets
- [ ] **Malformed-packet policy tests** (the router already drops and logs; the new channel matches it), plus the identity model: session-scoped peer ids remain the transport view; the stable Account ID (§3.12a) is mapped onto them at the handshake
**Acceptance criteria:** The trust model is written and implemented to its minimum: a plaintext session says so, a gated session refuses a bad token, and malformed input is dropped with a log line under test.
**Difficulty:** 🟠 decision + minimum implementation

### Milestone 10.10 — Simulation ownership & data subservers
*The resource model, decided: players' machines simulate the players, and a small data-authority **subserver** owns exactly the state a lot declares as protected. The host stops paying for player physics; the authority stays only where cheating actually costs something.*
- [ ] **Ownership matrix (the §10.6 movement item generalized):** local player body → own client (client-authoritative by default; opt-in host clamps); remote positions → originating client, relayed by the host; world objects/NPCs → host; **protected data domains** (currency, inventory, stats, progression, save slots) → the data subserver
- [ ] **Creator declaration:** a lot declares which domains are subserver-owned; everything undeclared stays host/peer territory. Routing stays a **deployment detail of existing `net.server` handlers — no new creator vocabulary in §3.2** (decided)
- [ ] **Deployment-transparent:** embedded in the host (default) ↔ sidecar process ↔ remote (§15 provider). Creator code does not change when it moves; the host↔subserver link is an internal seam
- [ ] **Sidecar mechanics:** the subserver is the same binary (`--subserver`), spoken to over the **existing loopback transport** (dogfooding §10.1's seam, plus a local token); supervision is explicit — who restarts whom, and what a session does when the data layer dies (writes stop, the session keeps running with a readable state)
- [ ] **Audit v1:** append-only JSONL per lot; hash-chained entries (each carrying the previous entry's hash) are the small, standard tamper-evidence upgrade; retention and visibility are a product decision documented with §3.12
- [ ] **Write rules:** clients send **intents** ("spend/buy/claim"), never state assertions; the subserver validates, rate-limits and keeps an audit trail; §1.3's host-authoritative rule applies at the subserver exactly as at the host
- [ ] **§3.12 tie:** the data subserver is the per-player datastore's storage home — its design doc is written against this model
**Acceptance criteria:** With two clients and a subserver: a spoofed protected-state write is refused and logged; the §10.5 harness shows host CPU without per-player physics; moving the subserver from embedded to sidecar changes no creator code.
**Difficulty:** 🟠 matrix + declaration + intent API · 🟠 sidecar lifecycle + remote auth (TLS + token) · 🟡 audit v1 (hash-chained JSONL) and intent idempotency · ⛔️ provider multi-tenancy deferred to §15

### Milestone 10.11 — Private servers & authorized hosting
*A lot can be played off an operator's own machine, for a trusted group — the private-server shape, running as a deployment mode of §10.10 rather than a fork of it.*
- [ ] **Local mode:** session + subserver on the operator's machine; client-authoritative physics everywhere; relaxed validation knobs (the operator is trusted — movement cheats on a private instance hurt no one)
- [ ] **Join:** invite/allowlist; never publicly listed; the §10.7 join flow applies unchanged
- [ ] **Authorization is per lot, creator-decided** (decided): `open` lots always permit private hosting; protected lots (§10.12) check a host token before the session starts
- [ ] **What still holds in relaxed mode:** protected-domain intents still validate (data integrity is not trust-dependent), and player-side content rules (scopes/ciphertext) still apply to joining players
**Acceptance criteria:** A player runs their authorized lot as a private server for friends with no Provider; an unauthorized attempt on a protected lot is refused with a readable reason; nothing is listed publicly.
**Difficulty:** 🟠 (deployment mode over §10.10)

### Milestone 10.12 — Content protection & anti-piracy
*The honest goal, stated once: a stolen copy is a **non-functional shell** — casual extraction and unauthorized hosting fail, authorized-host leaks are traceable, and nothing here claims to be unbreakable DRM. OpenLot is open source: the client engine is public by design, so this milestone protects the **creator's lot** — content, logic and data — not the platform. Godot's own docs say it plainly ("no out-of-the-box way to prevent someone from copying... DRM is your responsibility"), and its PCK encryption is a key-in-binary speed bump; we do not lean on engine obfuscation at all.*
- [ ] **Strongest lever — don't ship the sensitive half:** host/subserver-scope content (§10.10) and protected data never reach clients; what a client holds is presentation + prediction, worthless standalone. Script **distribution scopes** (which archive entries may stream to peers) are the mechanism; their storage form (prefix-based like `Secret_*`, or a v2 per-record field) is decided with §4.1's next format touch
- [ ] **Encrypted archive v2** (`.lot`): AES-256-GCM per entry via .NET (`System.Security.Cryptography` — Godot's `Crypto` is asymmetric-only, no AES-GCM, and this adds no dependency); a per-lot content key **never stored in the archive**, delivered through signed license tokens to authorized hosts and re-keyed per session for players; **client caches hold ciphertext only** (§10.7's rule). Rotation = re-encrypt + re-issue, carried by the §4.1 version gate with the usual migration discipline. **Open-default (decided):** open lots stay plaintext; protection is opt-in presets — *open / authorized hosts / private-group / provider-only*
- [ ] **Host authorization & licensing:** session-start check per preset with an offline grace lease so legit hosts are not bricked; failure = refuse **or** degrade (watermarked, no player data) — the creator's choice
- [ ] **Integrity & provenance:** signed manifests; §10.1's version handshake; traceable delivery identifiers — the per-licensee tokens are the trace, plus unique per-delivery canary markers and delivery records; kept honest about what they can prove (a determined leaker strips markers). Robust invisible asset watermarking (Denuvo TraceMark-class) is **parked as optional research — non-blocking, droppable with a note**; §16.10 license metadata rides the lot
- [ ] **People & legal:** provider policy hooks (§15.1), in-client reporting/takedown (§11.2/§11.3), license terms attached; sanctioned plugins/mods (§13) are allow-listed per lot — everything else is tampering
- [ ] **The honest matrix goes in the doc:** unzip → ciphertext; player-side drag-and-drop reuse → nothing to reuse (scoped); unauthorized host → no key/license; authorized-host dump → plaintext but still no data/logic when the subserver is remote; in-session cheating → intents validated (position cheats remain where physics is client-owned, by the §10.10 decision)
**Acceptance criteria:** An encrypted lot is gibberish without its license; a session's players cannot reconstruct the lot from their machines; an unauthorized host is refused; the leak-path table (what each attack gets) is written down, not implied.
**Difficulty:** 🟠 format crypto + scopes (rides §4.1's versioning) · 🟠 license/host-authorization plumbing · 🟡 traceable delivery identifiers + canaries (the already-planned tokens; delivery records are schema work) · 🟡 visible watermark / degrade mode (the existing fail-soft path) · 🔬 parked optional research: invisible forensic watermarking

## 12. Mobile Support (Android)

*OpenLot on phones and tablets. The core is portable — Godot's Android export carries the renderer, physics and the same C#/Lua runtime, and the network path is §10's session model unchanged, so mobile is a client, not a new transport. What is **not** portable is the interaction model: every surface today assumes mouse hover, a right mouse button, a keyboard and freely positioned windows, and a touchscreen has none of those. Sits ahead of §13 by design — player reach on Android is a distribution question, the plugin tiers are a creator-ecosystem one — and the real work is the restructuring below, not the export.*

**iOS/iPadOS stays out of scope, by platform and by policy:** Godot .NET requires JIT, which iOS prohibits — that technical blocker would have to change first. Even then, iOS entry is funding-gated: keeping the Apple Developer Program membership paid, a test iPhone, and the signing/App Store labor all come out of donations before any iOS work is committed. (macOS — §12.5 — shares the membership dependency but not the JIT blocker.)

**Acceptance criteria:** A player on a phone navigates menus, opens the terminal and runs a command with the on-screen keyboard, joins a lot, moves their character, chats and changes settings — with no surface unreachable because it required hover or right-click.

## 17. First-Launch Setup *(Post-MLP)*

*The first thing a new user meets should not be a bare terminal prompt. On first launch OpenLot runs a short setup wizard before the main menu — theme, account and key settings in one place — with an explicit Skip that is respected forever, and a way to re-run it later from settings.*

### Milestone 17.1 — First-launch setup wizard
- [ ] First-run detection through the existing `user://openlot_settings.cfg` (a new `[setup] completed` flag next to `[wallpaper]` / `[theme]` — not a second format); the wizard shows exactly once, before the main menu, and only while the flag is unset
- [ ] Explicit Skip for the whole wizard, plus per-step skip — skipping is a first-class choice that sets the flag, never a nag screen; a "Run setup again" entry in settings (§5.4) re-opens it any time
- [ ] Lean step set, each writing through the service that already owns it: theme pick (§5.4 presets — Green Matrix, Amber Retro, neutral), account (register/login or continue offline, §5.1 auth gate), and key settings (sensitivity/FOV, §5.4) — no step invents its own storage or its own widgets
- [ ] On Android (§12) the wizard is the very first surface and must be fully touch-workable from day one
**Acceptance criteria:** A fresh install launches into the wizard; skipping lands on the main menu and never shows the wizard again; completing it persists the theme, account and settings choices; re-running from settings works.
**Difficulty:** 🟡 (thin flow over existing services)

## 18. Package Management *(Post-MLP — first customer: §13.1)*

*One manager for everything installable — terminal apps (§13.1), creation-environment plugins (§13.2), and later assets/templates — so "install" means one thing across the app. It is also the trust boundary: what a package declares (its tier) is what it may do, and what a registry signs is what the user is shown. The trust model gets a decision doc before code, at the §3.2 bar.*

### Milestone 18.1 — Package format, registries & trust model
- [ ] A signed package bundle: manifest (id, version, semver dependencies, declared tier, publisher key), the tier-appropriate payload, and a checksum — a versioned format from day one (the `.lot` versioning discipline, §4.1, applies here)
- [ ] Registry protocol for list/search/fetch plus an offline path (install from a local file) so a registry outage is not a dead end; registries are configurable (a §15 provider can host its own) with a sane default
- [ ] Trust baseline decided in a decision doc before code: publisher signatures, what "verified/unverified" means at install time, key rotation, and the tier a package may request — the install prompt shows tier + publisher + signature state, and §1.4's tiers are enforced at load, not just displayed
**Difficulty:** 🔴 trust model · 🟠 format + protocol

### Milestone 18.2 — The manager itself (CLI first)
- [ ] `pkg install / remove / update / list / search / info` as terminal commands, reporting through §5.8's streaming output; installs are atomic (a failed install leaves the previous state intact) with a dry-run posture that suits a terminal
- [ ] A local installed-package store with pinned versions + a lockfile, so "it worked yesterday" is reproducible; update shows what changed before applying
- [ ] Runtime wiring per tier at install/uninstall: Tier 1 commands register with the command surface (metadata incl. the auth class §5.1's gate needs — today `Command` carries none), Tier 2 plugins register properties/panels/tools through §13.2's defined API only; uninstall reverses exactly what install added
- [ ] Per-package config + data directories reserved now (layout decided with the format), so packages stop inventing storage; §5.4 settings only displays them
**Acceptance criteria:** A third-party terminal app and a Tier-2 plugin both install, appear, update and uninstall through the one manager without touching anything outside their declared tier; a failed install changes nothing.
**Difficulty:** 🟠 package store + atomic installs · 🟠 tier wiring

### Milestone 18.3 — Package UI & moderation hooks
- [ ] A browser/install surface (EZLot §15.4 is the natural host; the terminal stays the power-user path) showing tier, publisher, signature state and permissions before install — the same data the CLI prints
- [ ] A reporting route for malicious or broken packages into §11.3's in-client reporting, and a provider-facing registry policy hook (§15.1 owns policy, never the core — §1.3)
**Difficulty:** 🟠 UI · 🟡 reporting hook

## Implementation Index — Milestone 3.2 (`net.*` + per-entity scripts)

Full decision record, execution flow and limitations: **`docs/design/milestone-3.2-unified-script-model.md`**.
Creator-facing reference: **`docs/net-api.md`**.

**Where the pieces live** (all under `builder/`):

| Piece | File | One-line contract |
|---|---|---|
| VM bootstrap + sandbox | `builder/script/LuaBootstrap.cs` | The Lua chunk: default-deny whitelist, sealed metatables, `makeNet(handle)`, validation pre-pass, watchdog hook, env loader, cross-entity sugar. Everything here is sugar over the bound `LotLuaApi` methods — no Godot access from Lua (§1.1). |
| Watchdog | `builder/script/LuaWatchdog.cs` | Instruction budgets (200k/dispatch, 1M/script load, 4M/frame, 3 trips ⇒ circuit breaker). Hook installed **from Lua**; always cleared **from C#** first. |
| Memory guard | `builder/script/LuaMemoryGuard.cs` | `lua_setallocf` hard cap (64 MB), `OomHit` flag checked after every dispatch, VM rebuilt at a frame boundary. |
| Net bridge | `builder/script/LuaNetBridge.cs` | `IDispatchTarget`: decode args onto the raw Lua stack, dispatch, trip counting, script-name registry, OOM/deferred rebuild, script loading. |
| Router | `builder/net/NetRouter.cs` + `builder/net/NetTransport.cs` | Transport-agnostic envelope/queue/rate-limit/authority core; `INetTransport` is the §10 seam (`LoopbackTransport` today). |
| Wire codec | `builder/net/NetSerializer.cs` | Argument tags, table array/pair sections, all budgets, stack-based decode, wrapper disposal. |
| Script runtime | `builder/script/ScriptRuntime.cs` | Script discovery, per-script envs, deterministic handle order, lot-root-at-load, frame `Tick`, teardown. |
| Lifecycle | `builder/script/LuaManager.cs`, `BuilderScene.cs` | VM lifecycle/scratch path (`RunString`) and the lot world: handle registry (root = 0), load-order handles, script load via `StartScriptRuntime` (restartable — the §3.4 Test-mode re-entry seam), `_Process` tick, `StopScriptRuntime` in `_ExitTree` teardown order. |
| Verification | `tests/NetSelfTest.cs` + `tests/NetIntegrationTest.cs` | 169 unit checks (private Lua states only) + an opt-in 8-check heavy set (`OPENLOT_HEAVY_TESTS`) + 59 integration checks driving the REAL LuaManager/ScriptRuntime and live lot; all run headless under `#if DEBUG`. The fast set prints its wall-clock; integration waits a few physics frames, prints a "suite complete: N checks" line and exits non-zero if it aborts. |

**Invariants any future change must keep**
- Lua reaches C# only through `LotLuaApi`; `NetInvoke`/`NetRegister`/`CallServer`/`CallClient` are the only net entry points, and the raw table-taking forms stay out of creator reach.
- All net traffic is queued and dispatched from `NetRouter.Flush()`; nothing executes synchronously, and recursion must never become stack depth.
- Contract changes to bound methods, tag bytes, table sections or creator-visible names are breaking changes to creator-facing API — call them out, never slip them in.
- The watchdog hook is installed from Lua (error() is safe there) and cleared from C# after every unit; never throw managed exceptions through native Lua frames.

**Known limitations (see the design doc §6 for detail)**
- Scripts run at lot load only — hot re-attaching a script waits for §3.4 Test mode.
- Editor-spawned objects get handles only once a registration path touches them (option A covers everything present at load).
- `coroutine` is unavailable in scripts; single blocking built-ins cannot be preempted.
- Numbers cross as doubles (2^53 precision); an OOM rebuild loses script globals.
- **Native `lua54` is not packaged yet** — Lua runs only with a compatible `liblua54.so` on the library path; bundling it is required before Test mode ships.
- Load-time spawns are owned by their script and removed before a reload (F2 closed); handler spawns are unowned by design. Physics smoke-test timing sensitivity (F4, deferred). Scripting suspension is terminal until the lot reloads and shows as a red banner in the Viewport window.
- Origination rule: autonomous calls (lot load, start(), timers) are System in ALL modes; Player only inside an explicit interaction scope (`NetRouter.BeginPlayerInteraction`; Test mode: `SimulatePlayerInteraction`).

## Roadmap Execution Stages

The four phases below are the **execution order** and supersede the numeric section order: **Phase 1 is §4**,
which is hoisted in this document to sit right after §3.4 (see the banner and full section there). Phases 1–2 are
the MLP-critical path; Phase 3 (networking/headless) and Phase 4 (avatars/animation/audio) follow it, and the
per-milestone tags still govern what actually ships at MLP.

### Phase 1 — Core Storage & Pipeline (§4.1 / §4.2 — `.lot` Archive & `LotVFS`)
Everything durable depends on this, so it goes first: the single-file Zip `.lot` bundle (`manifest.json` /
`lot.json` / `scripts/` / `assets/`), the `LotVFS` streaming read path, versioning + migration, and autosave /
crash recovery to `user://autosave.lot`. Landing it here also **unblocks §2.5 (environment persistence, through
`lot.json`)**, **§2.4 (autosave, which lives inside §4.1)**, and hands §7.2 and §16.6 their embedded-asset read
path.

### Phase 2 — In-Session Input & Script Hooks (§3.7 / §5.2 / §5.3 — Attributed Input, Events, In-Lot Command UI & Lot UI Activation)
With a real lot now loadable, the next blocker is the missing in-session path from a player action to a script
handler: the in-lot command UI (§5.2), lot-UI activation / click routing and the new element kinds (§5.3), and
the `touched`/`clicked` event system carrying the §3.4 `BeginPlayerInteraction` attribution for input-driven
events — `clicked` and lot-UI presses (§3.7; the physics-side `touched` attribution lands earlier, with §3.7
itself). The input-driven half of all three shares one in-session blocker and lands together; event/timer
subscriptions ride in the archive's
`scripts/` (§4.1).

### Phase 3 — Networking & Headless Host (§10.1 transport + §10.7 join flow + §10.2 Tier A, with the §10.5 runner) · §10.8/§10.9 follow; §10.6 / §10.10–§10.12 are the post-MLP depth
Boot a `.lot` with no client (`--lot <path>`, no UI or rendering viewport nodes), stand up the real transport
behind `INetTransport` in place of `LoopbackTransport`, and land the host/join/leave session model, session
content delivery and the naive state sync (the scaling pass is §10.6). `playerJoined`/`playerLeft` (§3.7), the
§3.12 per-player data ownership model (answered by §10.10's data subservers) and the §10.3 chat surfaces
unblock here, and the visual SSH host setup (§10.4) is the first consumer of the headless runner (§10.5).
The transport research pass is done (Oct 2026 — see the §10 baseline and its results section); the remaining genuine uncertainty is real-world NAT coverage (§10.2 Tier B — measured ~80% on cone NATs, ~40% on symmetric, which is why the relay exists) and interpolation feel (§11.4's check).

### Phase 4 — Avatars, Animations & Audio (§7.1 / §7.2 / §8.1 / §8.2 — Rigged Characters & GLTF, `.lanim` Tooling, 3D Audio)
The visible/audible layer, once Phase 1 can ship the assets and Phases 2–3 can drive and replicate them:
R6-style rigs + `.avlot` (§7.1), runtime GLTF/texture loading from the archive's `assets/` (§7.2), the `.lanim`
